MahinaOS Engineering Audit
Executive Verdict

MahinaOS is a real, partially-working systems project with a broken build story and an overstated README. The init system, compositor core, and package-manager crypto are genuinely implemented and pass real tests. The GUI/desktop layer is real too, just written in Rust instead of the C17 the README still claims. Nothing in this repo is faked or mocked in the "prints a success message and does nothing" sense — I went looking for that specifically and didn't find it. But a clean git clone does not build with the toolchain the project itself mandates, the test harness lies about its own pass/fail state, lint has never passed, and one headline README claim (malloc-free splash) is flatly false. This is "OS engineering fundamentals used sloppily," not "OS engineering faked."

What Actually Exists

Repo is 84MB, mixed C17 (systems core) + Rust 2021 (userspace GUI apps), workspace-organized. Concretely on disk and building (after my patches — see Build Results):

luna-init — statically-linked PID 1, C17, ~20 files
luna-init-ctl — CLI control client
luna-splash — framebuffer boot splash
lgp-compositor — DRM/KMS compositor, custom TLV wire protocol ("LGP")
luna-ai-d — daemon that proxies to a local Ollama instance
lpkg — package manager with Ed25519 signature verification (libsodium)
lgp-rs, lunagui-rs, luna-shell-rs, and 8 more Rust crates — GUI toolkit, shell, settings, files, calc, text, tasks, about, island, setup apps
kernel/.config — a Linux kernel config fragment (not a from-scratch kernel — confirmed, see §5)
boot/limine.conf — 5-line Limine bootloader config

Build/Test Results

Build status: PARTIAL. Clean clone did not build. Required 6 source patches to get every C component compiling under the project's own mandated flags (clang, -Wall -Wextra -Werror -Wpedantic):

Missing <sys/wait.h> in supervisor.c (undeclared waitpid)
Dead sleep_ms() function triggering -Wunused-function in supervisor.c
Missing <stdbool.h> in luna-ai-d/inference.c
Missing <sys/stat.h> in lpkg/main.c
Malformed nested comment (/* inside a block comment) in luna-splash/frames.h
Vendored stb_image.h violating the project's own -Wcast-align/-Wunused-function rules (nobody exempted third-party code from strict flags) — required #pragma suppression, still not a real fix, just a workaround

After patching: luna-init, luna-init-ctl, lgp-compositor, luna-ai-d, lpkg, luna-splash all built and linked. Link-time warnings noted: static linking + getpwnam/getgrnam/getaddrinfo (NSS lookups don't reliably work in static binaries — a real correctness risk for the "must be static" luna-init).

Rust workspace: Unable to verify fully. Cargo.lock requires a cargo newer than what's installable via apt on Ubuntu 24.04 (lockfile v4); rustup install is blocked by this sandbox's network egress allowlist (only registry/package mirrors are open, not sh.rustup.rs). Regenerating the lockfile and pinning older libc still hit toolchain-incompatibility errors (apt's rustc 1.75 vs. modern crate code). This is a sandbox limitation, not a confirmed Mahina defect — I read the Rust source directly instead (see below) and it looks legitimate.

Test status: PASS (substance) / FAIL (reported). All 15 Unity unit tests pass (log, TOML parser ×3, depgraph ×3 including cycle detection, service lookup, LGP protocol ×7). But make test-unit still prints FAIL and exits nonzero, because the Makefile has CRLF line endings (confirmed via file) that corrupt its own multi-line shell recipe, breaking the $failed variable check ([: -eq: unexpected operator). Repo has no .gitattributes and a mix of CRLF/LF across 19+ files — this isn't cosmetic, it broke the actual test harness.

Fuzz status: PASS. TOML parser and LGP-TLV fuzzers both ran for real (up to ~4.6M execs), no crashes.

Lint status: FAIL. make lint (clang-tidy, --warnings-as-errors=*) produces 36 errors on a clean tree. Most are pedantic (lowercase hex/int suffixes, narrowing conversions), but two are real bugs: a duplicate #include <string.h> in scene/surface.c, and a genuine dead-code switch-case clone in luna-init/main.c.

QEMU boot status: NOT TESTABLE. No qemu-system-x86_64 binary in this sandbox, no KVM, and actually booting requires building a full Linux 6.9.7 kernel from source per scripts/build-kernel.sh — multi-gigabyte download from kernel.org, which isn't in this environment's network allowlist, plus a Btrfs+FAT32 disk image build. Genuinely out of scope for this sandbox, not a finding about the project.

Code Quality

Sampled boot/init/compositor/splash/lpkg/GUI code directly (not just the lint run above).

Positive: consistent error handling in C (checked return values, errno-aware messages), correct privilege-drop ordering in supervisor.c (setgid→setgroups(0,NULL)→setuid), real async supervisor design (scheduled_start_ms restart backoff, not blocking sleeps), real fuzz harnesses wired to real parsers.
Negative, concrete:
Static linking + NSS-dependent calls (getpwnam, getgrnam, getaddrinfo) is a real portability trap — these silently misbehave in statically linked binaries at runtime depending on the host's /etc/nsswitch.conf, and luna-init is required to be static per its own docs.
lpkg's fail-open signature verification is a real security-hygiene issue, not just a "TODO."
Mixed line endings with no .gitattributes — this actually broke functionality (test harness), not just diffs.
Vendored third-party code (stb_image.h) compiled under the project's own strict warning flags with no exemption — a build-hygiene miss that any CI run would hit.
Dead code left in place (sleep_ms in supervisor.c) that only surfaces because -Werror is theoretically on — suggests the flags are aspirational rather than continuously run.
Comparison With Mature OS/System Projects

Not comparing feature count — comparing practice.

musl/BusyBox-style discipline (small, static, dependency-light) is the aspiration and luna-init genuinely follows it in spirit (static binary, no libc bloat beyond glibc's static-link caveats).
systemd-style declarative service TOML + dependency graph is architecturally sound and Kahn's-algorithm cycle detection is a legitimate design choice, correctly tested.
Where it falls short of any serious C project (Linux, FreeBSD, OpenBSD, systemd, musl all clear this bar): a green CI badge that's actually green. Every mature systems project treats "warnings are errors" as a gate that's continuously enforced on every commit; here it's a policy stated in docs that the actual tree doesn't currently satisfy. Real OS projects also don't compile vendored libraries under their own strict internal lint rules — they isolate third-party code specifically to avoid this class of problem, which is Packaging 101 that got skipped here.
Arch-style distro practices (declarative package definitions, signed packages) are present in spirit in lpkg, with real crypto, but the fail-open default is the opposite of Arch's/Debian's actual trust model.
Biggest Problems
Critical — Clean checkout doesn't build with the mandated toolchain. This is the single most damaging finding: it means the CI pipeline, as configured, could not currently be green on a fresh clone.
Critical — Test harness reports failure even when tests pass (CRLF/Makefile bug), meaning nobody can currently trust make test-unit's exit code.
High — lpkg package verification fails open by default (no pubkey = unsigned installs allowed silently).
High — Static linking combined with NSS-dependent libc calls (getpwnam/getaddrinfo) in luna-init/lgp-compositor — a real runtime correctness risk on target systems with non-trivial NSS config.
Medium — README materially misdescribes current architecture (GUI/shell are Rust, not C17; splash isn't malloc-free).
Medium — No repo-wide line-ending normalization; already caused one concrete functional bug.
Medium — Vendored code compiled under strict first-party lint flags with no isolation — will recur with any future vendored dependency.
Medium — Rust workspace couldn't be independently build-verified in a standard sandboxed environment due to a modern Cargo.lock (v4) requiring tooling this audit couldn't install — worth checking that contributors/CI actually have a matching toolchain pinned somewhere (rust-toolchain.toml doesn't appear to exist).
Low-Medium — luna-ai-d's HTTP parsing of Ollama's stream doesn't visibly account for chunked transfer-encoding framing; unverified but worth a real integration test against a live Ollama instance.
Low — Legacy (non-atomic) DRM modesetting in the compositor — acceptable and explicitly called out as an M1-scoped decision in the project's own docs, not a hidden gap.
What Is Genuinely Impressive
luna-init is a real, from-scratch PID 1 with a correct-looking async supervisor, signalfd/epoll event loop, and actual cycle-detecting dependency resolution — that's non-trivial systems work that a lot of "custom OS" hobby projects never get to.
The LGP compositor protocol has been independently reimplemented client-side in Rust using the same low-level primitives (memfd_create, mmap, SCM_RIGHTS) as the C compositor server-side. That's a real, working custom IPC/display protocol, not a Wayland reskin.
Real fuzzing infrastructure that actually ran and found nothing — most side projects claim fuzzing and never actually wire it up.
lpkg's crypto is textbook-correct Ed25519 usage via libsodium, hex/raw key format handling, proper detached-signature verification.
The project's own internal self-audit docs are more honest than the README — that's a good sign about the engineering culture even though it means the README needs fixing.
What Is Missing

Already solved: init/service supervision, TOML config parsing (fuzz-tested), basic DRM/KMS modesetting, core IPC protocol + shared-memory buffer passing, Ed25519 package signing primitives.

Partially solved: GUI toolkit and shell (real code, unverified end-to-end due to toolchain gaps in this audit — needs someone to actually run it on real hardware/VM with GPU passthrough), AI daemon (functional prototype, streaming correctness unverified), CI (workflow exists, doesn't currently pass).

Completely missing: AppArmor/seccomp profiles (kernel support only), actual audio/network/power-management subsystems (currently just service pointers to external Linux daemons — this is fine as an architecture choice, but should be labeled "integrates with Linux userspace" not "Mahina implements"), any Wayland/atomic-modesetting upgrade path, hardware driver work beyond what DRM/KMS gives for free.

Nice-to-have: input libinput/libudev support (currently raw evdev fallback), screen lock (luna-lock, zero code per project's own snapshot).

Final Verdict

An experienced Linux/OS engineer looking at this would be genuinely impressed by luna-init's supervisor design, the cross-language LGP protocol reimplementation, and the fact that fuzzing is real and wired up — those aren't things most 16-year-olds building a "custom OS" get anywhere near. They'd immediately clock it as experimental the moment they ran git clone && make all and hit a build error on line one, then found the test suite lying about its own results, then found a security control that fails open by default, then found the README describing components in a language they're not written in anymore.

"Is MahinaOS currently a real OS?"

PARTIALLY. It has a real custom init system and a real (if young) custom display protocol and compositor running on top of a stock, custom-configured Linux kernel — that's the "Linux-based OS environment" category, not "from-scratch OS" and not "just a desktop shell." What it is not, currently, is a bootable, demonstrably-working system: nobody in this audit (including me, in this sandbox) has proven it boots, and the build/test/lint pipeline that would normally provide that confidence is currently broken on a clean checkout.

"What percentage of the project is currently genuine OS engineering versus shell/UI/prototype work?"

Rough engineering estimate:

Real, tested OS-layer functionality (init, service supervision, IPC/compositor protocol, package crypto): ~35%
Real but unverified-in-this-audit (Rust GUI/shell, AI daemon streaming correctness): ~20%
Documentation/planned/zero-code (AppArmor profiles, luna-lock, atomic KMS, most of "AI-native" vision beyond the Ollama proxy): ~15%
Linux-provided functionality presented via Mahina service definitions but not implemented by Mahina (pipewire, NetworkManager, dbus, ntpd): ~15%
Build/release/test infrastructure that exists but doesn't currently function as claimed: ~15% (this is the category that should be smallest and isn't)

Mahina owns: init, the display protocol and compositor, the GUI toolkit, the shell, the package format/signing. Linux owns: the kernel, memory management, scheduling, VFS, the actual network stack, and (via pipewire/NetworkManager/dbus) most of what a user would call "the OS" in daily use. That's a legitimate and honestly-scoped custom-OS-environment-on-Linux project. It's just not, right now, one you can prove works by running the commands its own README tells you to run.
